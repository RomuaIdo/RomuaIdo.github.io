## Contexto e problema

No Campus Curitiba Sede Centro, reservar uma sala depende de e-mail ou de ir pessoalmente ao responsável. Professores, alunos de projetos e tutores não têm como ver a ocupação antes de pedir. O SOL é uma plataforma de autoatendimento: cada usuário vê a grade, solicita a reserva e o gestor de salas aprova ou rejeita.

O projeto foi especificado antes de ser codificado: plano de projeto com requisitos, doze casos de uso, diagramas de classes, comunicação, estados e atividades, e dicionário de dados.

## Arquitetura e decisões técnicas

```ascii title="Papéis e permissões"
 ALUNO  <  PROFESSOR  <  TUTOR  <  GESTOR
   |           |           |          |
   |           |           |          +-- aprova/rejeita reservas e projetos,
   |           |           |              mantém usuários, salas e disciplinas
   |           |           +-- registra projetos, acompanha os próprios pedidos
   |           +-- reserva salas (dia ou semestre), acompanha os próprios pedidos
   +-- consulta a grade; como membro de projeto, informa horários livres
```

**Papéis como hierarquia ordenada.** As permissões seguem um ranking único (`ALUNO < PROFESSOR < TUTOR < GESTOR`), então cada verificação é uma comparação, não uma lista de exceções espalhada pelas telas. Uma rota protegida declara o papel mínimo.

**Front-end primeiro, com camada de serviços.** As páginas falam apenas com serviços tipados (`salaService`, `reservaService`, `projetoService`, ...). Nesta fase os serviços usam um banco simulado persistido em `localStorage`; a API em Java 17 + Spring Boot 3 está planejada e entra atrás da mesma interface, sem reescrever as telas.

**Reserva diária e semestral como fluxos distintos.** A reserva de um dia pode ser consolidada direto; a semestral sempre gera uma solicitação pendente para o gestor.

## Implementação

Fui responsável pela arquitetura do back-end e do front-end, incluindo a separação entre páginas e serviços descrita acima, e por parte da codificação, concentrada nas regras de negócio:

- Correção da hierarquia de papéis e do acesso ao dashboard: o gestor gerencia todas as solicitações; professor e tutor acompanham apenas as próprias, em modo leitura. Só o gestor vê os botões de aprovar e rejeitar.
- Cobertura de todos os casos de uso da especificação, incluindo o registro de projetos por tutores e a opção de o criador entrar como gestor do projeto.
- Mapa de calor da disponibilidade do grupo, cruzando os horários livres informados pelos membros de um projeto.
- Ajustes no modal de reserva (data e hora separadas) e uma migração do banco simulado que adiciona novos usuários de teste sem apagar os dados já salvos no navegador.
