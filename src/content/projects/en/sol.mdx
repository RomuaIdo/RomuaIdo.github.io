## Context and problem

At Campus Curitiba Sede Centro, booking a room depends on email or going in person to the person in charge. Professors, project students and tutors have no way to see occupancy before asking. SOL is a self-service platform: each user sees the schedule grid, requests the booking, and the room manager approves or rejects it.

The project was specified before being coded: a project plan with requirements, twelve use cases, class, communication, state and activity diagrams, and a data dictionary.

## Architecture and technical decisions

```ascii title="Roles and permissions"
 ALUNO  <  PROFESSOR  <  TUTOR  <  GESTOR
   |           |           |          |
   |           |           |          +-- approves/rejects bookings and projects,
   |           |           |              maintains users, rooms and courses
   |           |           +-- registers projects, tracks own requests
   |           +-- books rooms (day or semester), tracks own requests
   +-- views the grid; as a project member, reports free time slots
```

Role names are code identifiers: ALUNO (student), PROFESSOR (professor), TUTOR (tutor), GESTOR (room manager).

**Roles as an ordered hierarchy.** Permissions follow a single ranking (`ALUNO < PROFESSOR < TUTOR < GESTOR`), so each check is a comparison, not a list of exceptions scattered across the screens. A protected route declares the minimum role.

**Front end first, with a services layer.** Pages talk only to typed services (`salaService`, `reservaService`, `projetoService`, ...). In this phase the services use a mock database persisted in `localStorage`; the Java 17 + Spring Boot 3 API is planned and will go in behind the same interface, without rewriting the screens.

**Daily and semester bookings as distinct flows.** A one-day booking can be confirmed directly; a semester booking always generates a pending request for the manager.

## Implementation

My contribution focused on the business rules:

- Fix of the role hierarchy and of dashboard access: the manager handles all requests; professor and tutor only track their own, in read-only mode. Only the manager sees the approve and reject buttons.
- Coverage of all use cases in the specification, including project registration by tutors and the option for the creator to join as project manager.
- Heat map of group availability, crossing the free time slots reported by the members of a project.
- Adjustments to the booking modal (separate date and time) and a migration of the mock database that adds new test users without erasing the data already saved in the browser.
